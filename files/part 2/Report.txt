Software Architecture Diagram (Cameron Will).


The client talks only to whichever node currently owns TCP port 8000. The primary writes its state to an HMAC-protected checkpoint after every change and sends heartbeats over UDP to the monitor. When heartbeats stop for 3 seconds, the monitor (1) fences the old primary by killing its PID and (2) starts a standby. The standby verifies and loads the checkpoint, takes over port 8000, and resumes heartbeats as the new primary.

Redundancy Justification (Cameron Will).

We chose passive redundancy (warm standby with checkpointing) over active redundancy. Our service’s state is small (active session tickets, failed-login counts and lockouts), so the primary can write a complete checkpoint after every change at almost no cost. That avoids the main overhead of active redundancy: copying every client request to a second running node and keeping both in lock-step over a sync channel. Passive redundancy was also simpler to build and easier to secure. Only one node is ever authoritative, so we avoided the request-ordering and duplicate-response problems active replication brings. Split-brain prevention reduces to one rule: the monitor kills the old primary’s PID before it starts the standby. The trade-off is a non-zero Mean Time to Repair. MTTR is the 3.0 s detection window (W = N × T) plus the time to start the standby and load the checkpoint, so about 3–4 s, compared with near-zero failover for a hot spare. Because we checkpoint after every change rather than on a timer, no state updates are lost. An authentication service can tolerate a few seconds of retries from clients, which our client handles automatically. It cannot tolerate forged or corrupted security state, so we put our effort into checkpoint integrity (HMAC verification with fallback to the last good copy) and fencing instead of the speed of an active replica. Passive redundancy also leaves a risk active redundancy shares: a malicious “poison-pill” request that crashed the primary could crash every new standby too. We limit that with a crash-loop guard: after 5 failovers in 60 seconds, the monitor stops automatic failover and asks for a human.
