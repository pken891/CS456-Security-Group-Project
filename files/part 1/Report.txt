Service Overview (Cameron Will):
The critical service, auth-ticket-daemon (files/service.py), simulates an authentication server similar to a Kerberos KDC. Each cycle, its main thread receives a simulated login request, checks the credentials against salted password hashes, and issues a 128-bit session ticket on success. A separate background thread sends a JSON heartbeat over UDP to the monitor at 127.0.0.1:9999 once per second (T = 1.0 s). Because it runs apart from the authentication loop, slow logins cannot delay heartbeats and trigger false alarms. To model an unpredictable production failure without a fixed crash point, every cycle checks random.random() < 0.08. When this fires, the service logs a fatal segmentation-fault message about a malformed authentication payload, with UTC and local timestamps, the cycle number, and the last heartbeat number sent. It then calls os._exit(1), which ends the whole process at once, including the heartbeat thread. The heartbeats simply stop, so the monitor sees only silence, as it would after a real crash. Each cycle lasts about one second, so the expected uptime is 1/0.08 ≈ 12.5 s. In our test runs, the service crashed after 5 to 30 s, and the monitor raised its alert 3.01 s after the last heartbeat.

Architectural Parameter Justification:

For our fault-detection architecture, our team implemented a Push-Based (Unidirectional Notification) heartbeat pattern over connectionless UDP (SOCK_DGRAM on 127.0.0.1:9999) rather than a Pull-Based (Ping-Echo) model. In this design, the critical Authentication/Ticket Service autonomously emits JSON liveness datagrams from a decoupled background thread, which cuts socket traffic in half compared to bidirectional ping-echo queries and ensures an abrupt process crash (os._exit(1)) never causes broken-pipe exceptions or crashes in the independent monitor. To calibrate timing, we configured a heartbeat emission interval of T=1.0s (1000ms), a missed-beat threshold of N=3 consecutive beats, and a sliding timeout window of W=3.0s (3000ms, where W=NT). This parameter calibration balances a fast 3.0-second Mean Time To Detect (MTTD) and minimal CPU/socket overhead against false-positive resilience, allowing the monitor to tolerate up to two delayed or dropped packets from transient OS thread-scheduling jitter before raising a critical crash alert. 


Adversarial Audit Summary:
	The baseline heartbeat channel is both unauthenticated and stateless, and the adversarial audit, which is held in “attackers.py” succeeded in both successful attacks against it.  The monitor accepts any UDP datagram sent to  the IP address “127.0.0.1:9999”  as a valid liveness signal as long as it its a JSON with the “HEARTBEAT” type. The monitor makes no effort to validate or authenticate the user due to the lack of a shared secret, HMAC, or digital signature. It also never filters on source address, never validates the payload’s timestamp field for freshness, and never requires the seq number to increase. Liveness is instead judged solely by the arrival time of packets, so anyone that can reach the loopback port is implicitly trusted. During the first attack, Heartbeat Spoofing, the auditor/attacker forges HEARTBEAT datagrams that match the service’s exact JSON schema and streams them to the monitor once per second. In our test runs the monitor reported the auth-ticket-daemon as HEALTHY and never raised a fault alert, even with no real service process running at all, because it cannot distinguish forged beats from genuine ones. In the second attack, Replay / Tampering, the auditor first captures a single legitimate heartbeat off the wire and then retransmits those exact bytes on a loop after the real service has been terminated. Due to the fact that the monitor performs no freshness or sequence-ordering checks, that means it accepts the recycled packet indefinitely. in testing it continued logging [OK] Heartbeat #1 with an identical, stale PktTime on every beat and never detected the crash. This shows that the timestamp field embedded into the payload isn’t actually effective.It travels on the wire but is never evaluated, so replaying stale status data is enough to mask downtime. Both of these attacks exploited the lack of authentication and state on the detection channel. The straightforward hardening is to add a pre-shared-key HMAC over each payload (defeating spoofing, since the attacker cannot compute a valid tag) together with a monotonically increasing nonce or a signed, monitor-verified timestamp (defeating replay, since stale or out-of-order beats would be rejected).
